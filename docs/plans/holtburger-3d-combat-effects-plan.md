# h3d combat outcome effects

Status: physical and scoped magic combat effects implemented and automatically verified (2026-10-11). Source census, integration dry run, implementation, verification, and cleanup are complete. Visual acceptance remains with the user.

## Context and boundaries

Show generally reliable, server-confirmed outgoing physical/magic damage, evasion, and spell resistance as short-lived JRPG-style floating text in the h3d client. Exact placement is cosmetic; fabricated damage or misses are unacceptable.

In scope: source census, outcome delivery, conservative target attribution, and a dedicated app-local combat-effects owner for lifetime and resources. Physical and magic coverage includes source-backed spell health damage, periodic health/nether damage, and explicit resistance, using the same owner. Healing, nonhealth vital changes, and unquantifiable transfer damage remain excluded. Out of scope: server/protocol changes, predicted damage, a generic effects framework, and visual acceptance by the agent.

**Correction to the earlier chat proposal:** a matching sent-target name alone is insufficient when cleave can hit another creature with that name. Prefer losing spatial placement over presenting guessed identity as a fact.

Implemented bounded resolver:

**Owner:** add `CombatOutcomeAttributor` in `crates/holtburger-core/src/client/combat_attribution.rs`, owned by the existing core combat runtime composition. It owns only bounded sent/recently retired target context, name corroboration, retained-creature ambiguity checks, and the resulting attribution decision. Keep context and attribution rules out of the client message dispatcher and frontend composition roots. `CombatEngagementRuntime` remains the authority for actual sent/retired engagements; the attributor observes those facts rather than independently recreating the engagement state machine.

Integration: `client/combat_runtime.rs` feeds the attributor actual send/retirement transitions. `client/messages.rs` asks it to resolve outgoing damage/evasion before publishing `ClientViewEvent::CombatFeedback`; the immutable result travels with the outcome. World/session reset clears its context. World supplies read-only entity facts, not attack correlation. The host transports the decision, and h3d never recomputes it. h3d may independently choose unplaced visual presentation if an attributed GUID no longer has a presentation position; that is a placement failure, not a revised attribution.

Keep the attributor as a private field beside `combat_engagement` in the existing `ClientRuntime` composition (`client/mod.rs:216`), initialized in both builders (`client/builder.rs:238,301`). The combat runtime is currently an `impl ClientRuntime` module, not a separate instantiated object; this field arrangement implements the ownership above without inventing a new runtime container.

The send boundary matters: `CombatEngagementRuntime::issue_desired_attack` sets `sent` before the async wire send (`combat_engagement.rs:229`; `combat_runtime.rs:398`). Call the attributor only after `send_targeted_attack(...).await` succeeds, not just when `next_effect` changes state. Failed sends must not create attribution candidates. At `observe_combat_feedback`, compare the engagement before and after `attack_done` and retire an actual candidate only when it is cleared/replaced; successful refill feedback does not retire it. Repeated same-target profile sends refresh the active record without accumulating duplicate GUIDs. Retiring/cancel-pending targets remain candidates until terminal feedback.

1. Retain one active successfully sent target plus bounded unique recently retired GUID/name candidates, within the current world generation. Active context does not expire merely because server repeat attacks continue without a new client send. Bound retired count and age using named combat-attribution tuning; expiry is a concession, not a network guarantee. Capture the world name at successful send so retirement does not require the entity still to exist. If the name was unavailable, keep identity unresolved rather than inventing a name.
2. Use retained `WorldState.entities.entities` (`crates/holtburger-world/src/state/types.rs:48`; `entity.rs:1755`) to detect other same-name creatures. Reuse the public creature classification (`EntityTargetingCategory::Creature`, `entity_facts.rs:198`) or its underlying public item-type predicate. Include same-name retained creatures conservatively even when they cannot currently be placed. Their presence is an ambiguity veto, never permission to attribute an unrelated creature.
3. Attribute only if there is exactly one matching distinct attack-context GUID and no different matching retained creature GUID. Multiple GUIDs or no matching attack context produce explicit unplaced feedback. Position availability is evaluated separately by h3d at intake. Do not choose closest, newest, or selected as a tiebreaker. Unique-name cleave secondaries without their own sent context remain unplaced in this first cut.
4. Emit the attribution decision with the outcome. It is best effort even when there is one known candidate: retention boundaries may hide an unknown same-name target.
5. h3d snapshots the attributed entity's presentation position at intake. If it no longer exists, use unplaced presentation. Never repeat name lookup in the browser.

This deliberately uses a simple event-time scan rather than a new name index or a guessed cleave radius. Existing `SpatialScene::get_nearby_entities` / `get_entities_in_range` (`spatial/scene.rs:1741,1769`) are available, but a range cutoff could conceal ambiguity. Accepted cost is linear in retained entities per outcome; measure only if it becomes material. Accepted presentation cost is more unplaced feedback, including duplicates too far away to actually be hit.

Use a discriminated attribution shape such as `Attributed { target } | Unplaced`; only add reason categories if a named display or diagnostic consumer needs them. No unbounded attack log, projectile predictor, or guessed packet-to-swing receipt.

## North stars

- Server outcomes own truth; attack completion is not an outcome.
- Attribution uncertainty must survive the contract; do not disguise a heuristic as authoritative identity.
- Shared core owns reusable combat semantics. h3d owns visual policy, effects, and resources.
- One focused combat-effects subsystem owns active effects; composition roots only wire it.
- Prefer reuse and bounded lifetimes over a new general-purpose particle abstraction.

## Proposed flow and lifetime

ACE outcome -> protocol -> core CombatOutcomeAttributor -> attributed combat feedback -> typed h3d host event -> app-local CombatEffectsSystem -> renderer draw instances.

### Concrete ownership

- Add app-local `lib/game/systems/combat-effects-system.ts`: one `CombatEffectsSystem` facade owns intake, active records, animation time, a hard active-effect budget, resource allocation requests, expiry, reset, and disposal. Its state belongs to the h3d presentation layer, never Rust core or Svelte `$state`.
- Add a focused renderer adapter, e.g. `lib/game/renderer/webgl2-combat-effects.ts`, for context-bound GPU resources. Expose a narrow `RendererCombatEffectsCapability` in `renderer.ts`, following the existing particle capability (`:839`): create an effects-owned resource handle, submit current instances, clear submitted work, and release the handle. The WebGL renderer constructs the concrete adapter with its context; `CombatEffectsSystem` retains the returned handle and releases it on disposal. Backend types/GL never enter the system or Rust contracts. The adapter owns actual textures/buffers; the facade owns when they live. The main renderer only routes draws through existing flat/portal visibility and retains a final teardown safety net. Release is idempotent to accommodate partial initialization/teardown.
- Prefer one small glyph atlas for damage digits, `MISS`, and `CRITICAL`, including the bounded outline variants needed for normal and critical styling, with tint/scale/opacity applied at draw time. This avoids one texture per damage value and lifetime churn. Atlas lives for the subsystem, active instance storage is bounded, and all resources release on subsystem disposal. Reset clears instances but can retain the atlas. Use browser Canvas text shaping/rasterization; do not implement fonts.
- Extract only the reusable billboard geometry/program portions of the nameplate pass when needed and migrate nameplates in the same change. Keep nameplate cache/population rules separate. If atlas UVs demand substantial shared-pass complexity, use a focused combat draw adapter with existing shader/program/portal helpers and document the duplication tradeoff before broadening the renderer abstraction.
- Intake captures canonical `SceneVector3` plus physical placement membership, never retained camera-relative positions, renderer scope keys, or node references. Add a narrow runtime placement-read API backed by existing dynamic placement/scene facts; transform the center of the realized entity's current rigid mesh bounds with no padding, excluding animation sweeps and particle-expanded culling envelopes, converting to scene coordinates at the producer. If there is no coherent position/membership at intake, use unplaced feedback. Resolve render-relative placement and current selected render scope keys from the retained physical membership each frame. Rise/fade/scale are derived from spawn time and tuning, not accumulated deltas. Entity removal does not delete a spawned effect.
- Age effects even when offscreen/hidden; portal routing is handled at the renderer boundary. Combat indicators disable scene depth testing and depth writes so geometry cannot obscure their centered text; portal-domain clipping still applies. Nameplates currently acquire scope keys through live selected dynamic contributions (`webgl2-renderer.ts:2758`), so that path cannot own effects that survive entity deletion. Route retained physical placement membership through current per-view portal visibility independently; when its physical domain is absent, skip world drawing while continuing expiry. Do not retain per-frame atlas/scope keys or quietly convert hidden world effects into the unplaced lane. Never show world text through unrelated dungeon cells merely because a GUID is known.
- Explicit unplaced feedback uses one bounded screen-space lane within the same subsystem, not a second toast/chat owner. It carries no implied target attachment. Proposed initial policy is to retain the confirmed outcome there; user can steer this cosmetic choice before implementation.
- Clear on every presentation discontinuity, including forced reposition within the same session; reject older world-generation events, reset core attribution history on generation change, and drop late intake after disposal. Same-generation target switches preserve already spawned visuals.

### Popup motion and critical-hit presentation

- Ordinary damage spawns at the attributed target's captured mesh center, briefly enlarges, settles to its normal size, rises gently, and fades near the end of its lifetime. Start with approximately one second total duration; exact duration, phase timings, travel, and scale belong in frontend tuning rather than behavioral invariants.
- Give successive popups a small bounded sideways spread chosen at spawn, so repeated hits remain readable. Retain that spread once; never reroll it per frame. World-space text stays camera-facing and drifts independently of the creature after spawning. Camera motion changes its projection normally.
- `MISS` uses the same pop/rise/fade sequence with muted styling. Unplaced outcomes use the same animation phases in their screen-space lane, with pixel travel rather than world-space displacement. Neither path adds physics simulation or target-following state.
- A server-confirmed critical hit displays the damage number with a larger initial pop and slight scale overshoot, a distinct warm color, a stronger outline, and a small `CRITICAL` label above the number. Color alone must not be the only distinction. Exact colors, outline widths, label size/spacing, and overshoot remain tuning choices for user visual acceptance.
- Treat the critical label and number as one logical effect: one spawn time, placement, sideways spread, budget slot, animation profile, expiry, and reset/disposal path. They may emit multiple glyph draw instances but must not become independently managed particles or a separate critical-effects subsystem.
- `CombatEffectsSystem` selects the normal/miss/critical appearance profile once at intake and computes rise, scale, and opacity from elapsed time. The critical flag comes from the confirmed outcome; do not infer it from damage size, sounds, or death. Killing-blow critical popups retain the existing notification coverage gap.

### Contract sketch

The outgoing feedback owns the existing damage/evasion payload and explicit best-effort attribution (`Attributed { target } | Unplaced`). Add producer-stamped `world_generation` alongside attribution on the outgoing feedback variants, preferably grouped as one documented outcome context type. Incoming/defender, death, and lifecycle feedback do not require cosmetic outcome context. The generation is read when core publishes feedback, never reconstructed from later host/browser state: `project_client_event` is pure and has no current-world-generation input. h3d derives one narrowed payload (`Damage { amount, critical_hit } | Evaded`) for its effects consumer. Chat formatting continues to consume the original full feedback. No duplicate event emitted from core and no fields without consumers.

Keep `project_client_event -> Option<ClientHostEvent>` and the host forwarding loop unchanged. For outgoing physical feedback, project a composite `ClientHostEvent::CombatFeedback { chat, outcome }`; in `host/src/protocol.rs`'s concrete `publish_client_event` boundary (`:442`), expand that one composite into the existing chat HostEvent followed by the new outcome HostEvent. Non-outgoing feedback retains its existing projection. This limits fan-out to the transport adapter and preserves the existing `client-chat-message` channel and probe behavior without changing all projection consumers. Propagate either publication failure; no silent partial-delivery retry or duplicate suppression layer.

Register the outcome HostEvent and event-name/payload types in `host/src/protocol.rs`, `src/lib/host/host-transport.ts:284,406`, and lifecycle transport/decoder subscriptions. Test the composite projection and concrete sink expansion, not just a Rust enum constructor. The TUI chat consumer (`apps/holtburger-cli/src/pages/game/panels/chat.rs:179,253`) ignores the added context and preserves chat; adapt constructors/matches and focused checks there as required by the shared contract change.

Producer generation tagging rejects queued old events, not server outcomes from old projectiles received after a teleport: the wire supplies no generation. After a reset, such an outcome has no prior attack context and is unplaced; even a same-name new engagement can remain observationally ambiguous. Do not claim this plan solves cross-teleport projectile identity.

Lifecycle: create -> accept event/spawn -> advance and submit -> lazily acquire atlas on first visible draw -> expire/reuse instance capacity -> reset/clear -> dispose adapter and CPU state. Failed allocation throws with cleanup; no silent replacement by misleading placement.

## Implementation decisions and verification evidence

- The effects wire payload carries amount and critical flag; damage type remains in full core feedback and chat because the visual profiles have no damage-type consumer.
- Attribution retains one nonexpiring active send and at most eight recently retired targets for eight seconds. These history bounds are a best-effort concession, not proof of projectile lifetime. Successful-send recording lives inside `send_targeted_attack` after the async send succeeds.
- `CombatEffectsSystem` owns bounded records and a renderer lease. Its adapter lazily builds one atlas with normal/critical outline rows and measured glyph advances/bearings. Only clip-space billboard offset math is shared with nameplates. Atlas UVs and per-glyph tint make a separate focused draw adapter smaller than broadening the complete-nameplate pass/cache contract.
- Runtime intake snapshots the current rigid mesh bounds center and physical scopes. Each draw resolves current camera-relative coordinates and selected portal domains from that snapshot. Duplicate physical scopes mapping to the same render domain draw once. Unplaced effects draw once after final composition, at the configured render density.
- Cosmetic time advances once at client frame entry even when scene readiness holds simulation. Other runtime callers explicitly advance the cosmetic clock; loading polls do not sample a second timestamp. Reset clears submitted instances while retaining the reusable atlas; disposal releases the lease before renderer destruction. Partial GPU initialization and normal disposal unbind owned shader programs before deletion because WebGL otherwise defers their release.
- Focused Rust checks exercise successful/failed send, active repeat context, duplicate-name veto, deduplication, retired history expiry/budget, generation reset, host projection, and ordered chat/outcome sink expansion. TypeScript checks exercise profiles, phase evaluation, spawn spread, budget, missing placement, target deletion, held-frame clock forwarding, resync/discontinuity gates, and disposal ordering.
- Browser verification is split across the real decoder/GPU fixture and a production runtime/renderer probe. The GPU fixture checks camera reanchoring, indoor physical scopes, deferred portal envelope occlusion, hidden expiry, normal/miss/critical rendering, both critical placements, logical-label glyph emission, lazy/shared atlas allocation, draw counts, reset, repeated owners, and resource failure cleanup. The runtime probe realizes a synthetic entity, accepts decoded critical feedback, removes the target, verifies retained placement and missing-target unplaced intake, clears, and ages without a world draw. Transport/resync behavior is verified through production lifecycle/presentation sessions with a synthetic transport in unit tests; these synthetic tests do not establish live magic compatibility or visual acceptance. The later physical live trace is recorded under User review.

### Owners and strict interpretation

**Reusable core semantics:** add `crates/holtburger-core/src/client/server_combat_text.rs`, a focused, stateless recognizer of these server message families. It accepts the raw `ChatMessageTypeId` and text, and returns an optional private parsed outcome carrying the defender name, any explicitly present spell name, and damage/critical or resistance facts. Its family discriminator is consumed by attribution routing. It owns no history, world queries, display strings, textures, or timing. Keep the network dispatcher limited to calling the recognizer and the attribution owner. Place the narrow runtime orchestration helper alongside existing combat methods in `client/combat_runtime.rs`; it converts the private parsed facts into the public typed outcome without adding state to `messages.rs`. Unknown numeric chat types are preserved by `ChatMessageTypeId` and must return no interpretation, not be coerced to Magic.

Use small anchored parsers with existing Rust string operations and checked `u32` amount parsing; this grammar does not justify a new parsing dependency. Accept only complete messages on the listed channels, exact ordered optional prefixes/suffixes, nonempty names, and the listed verbs. Treat defender/spell names as opaque strings: do not split on whitespace, normalize case, or strip legitimate punctuation. If delimiters permit multiple valid decompositions, decline recognition rather than guessing. Unknown formats, overflows, negative/fractional amounts, trailing junk, mismatched channels, incoming text, or multiple-family matches remain unchanged chat with no cosmetic outcome. Do not silently swallow internal errors; an unrecognized server template is a deliberate compatibility boundary, not an internal exception.

Recognize only at the actual network `GameMessage::ServerMessage` intake. Do not process local status text, speech/tells, formatted chat buffers, or scripting events. Parsing and attribution are separate: missing cast history or catalog data must not discard a fully recognized confirmed amount. Recognition produces no predicted event at send time.

**Attribution remains owned by `CombatOutcomeAttributor` in core**, beside the existing engagement runtime. Extend that owner; do not add a spell attribution owner in the browser, a universal combat controller, or a projectile predictor.

- Preserve the current nonexpiring physical active engagement and its bounded retired targets. Add a separate bounded recent targeted-cast queue within the same attribution owner. Casting must not overwrite the physical active target or require inventing a spell engagement state machine.
- In `combat_runtime.rs::cast_spell:714-738`, capture the prepared action's actual target and catalog spell name during validated preparation. The prepared request owns its validated catalog name, and `to_action(&self)` copies only the wire identifiers, keeping that identity available after the mutable async send; stamp history with the successful-send time. Self-target and untargeted casts supply no outgoing defender candidate.

Missing names never establish identity. No nonexpiring active spell target: casts are one-shot requests, and UseDone/busy completion does not bound projectile travel or DoT lifetime.

Periodic damage considers the union of existing physical and recent cast target context because its text omits a spell and includes proc/physical sources.
