## Context and boundaries

**Goal:** Support purchasing and maintaining housing through house crystals, and inspecting and managing the account's effective home through H3D's Housing tab.

### In scope

- Ordinary crystal interaction opens a purchase/maintenance HUD window from the server's profile response.
- Ownership-aware presentation: available, current-character owned, account-character owned, other owned, disabled, and maintenance-free/paid states.
- The crystal window has a compact owner/payment-status summary, a contextual Purchase or Maintain action tab selected by default, and a Details tab for dense noninteractive information.
- The action tab presents one row per applicable payment requirement: shared item cell, name, paid quantity, selected effective contribution, and outstanding quantity after the draft. Each row has an SVG auto-fill icon button. Dragging into its cell adds matching inventory sources; dragging its combined selection out clears that row locally. Preparing payment never submits or transfers items.
- Own-home information is queried during character initialization, retained throughout the character session, and refreshed by server updates. Tab focus does not query. Core also loads effective-home permissions and owns subsequent scheduled refreshes; Retry remains for unavailable information.
- The Housing tab displays home information and supports guest/storage permissions, public/allegiance access, guest booting, empty-hook visibility, and confirmed abandonment.
- Available-housing search is accessible from the World-map overlay for Cottage/Villa/Mansion, including when no home is owned. None hides results. Phase 5C replaces the older Housing-tab form; Apartments are omitted from this UI.
- Own-home map markers populate automatically for cottages, villas, and mansions. Coordinates stay visible in the Housing tab; there is no Show on map button. Apartments have no map marker.
- Existing toasts carry action rejections and unresolved transaction feedback.
- Verify existing hook container interactions; change them only for a demonstrated housing-related gap.

### Out of scope

- Reimplementing hook opening, item placement, or removal as a separate housing mechanism.
- New transport machinery, ACE feature implementation, or modifications to the retail decompile.
- Precise crystal listings from the available-housing response, apartment map placement, or a multi-home ownership list.
- Allegiance mansion administration beyond the personal home's allegiance-access controls.
- New home recall behavior, frontend redesign outside housing, or visual acceptance performed by the implementer.

## North stars and ownership

1. One authoritative retained representation per housing fact. HUD consumers never recompute payment, ownership, or deadlines.
2. Use existing interaction, inventory, container, busy-operation, feedback, and map paths. Avoid a generic transaction framework or a second hook system.
3. Account ownership identifies a relationship; it does not grant every management capability. The server remains the final authority.
4. Separate home information from the currently interacted crystal and from local payment drafts.
5. Server receipt is distinct from local dispatch. Never claim success merely because a command was sent or an unrelated UseDone arrived.
6. App-local presentation stays in H3D. Add focused shared housing modules rather than enlarging client orchestration functions.

| Layer | Owns |
| --- | --- |
| Protocol | Lossless wire structures, enums/flags, packing and unpacking only. |
| World | Retained housing/access facts; pure payment matching/consumption and maintenance semantics. |
| Core | Initialization/refresh, account ownership classification using the roster, action admission, inventory auto-selection, execution/reconciliation, and reusable commands/view contracts. |
| H3D host | Typed command dispatch and projection; no business-rule rederivation. |
| H3D session | Validated transport events and retained frontend snapshots; independent of DOM lifetime. |
| H3D UI | Draft selection, confirmation policy, window/layout/focus/range presentation, management controls, map markers, and toast display. |

No housing changes are expected in session, DAT, or content crates. Reuse current static/map/icon facilities. Every new field must have a named consumer; every type/field needs a comment.

The busy-routing consolidation is implemented in `client/busy_operation.rs`, including the housing payment PendingOperation and focused execution module. Admission, operation-specific UseDone/error interpretation, abort dispatch, and terminal completion/timeout publication use that owner. Remaining verification gates are listed in Phase 4; management must extend this routing rather than create a parallel inventory mutation lock.

The busy owner controls admission, deadline, cancellation, and publication. Each operation module owns which evidence constitutes completion and any continuation. Route before taking the pending operation: housing must retain its owner when an unrelated or delayed UseDone arrives. Preserve vendor's continuation behavior rather than flattening it into a generic success/failure callback.

Keep home query/loading, crystal interaction, and payment execution as separate lifecycles. A home query does not acquire the inventory mutation lock; closing a crystal window does not cancel submitted payment reconciliation. Share pure facts and operation routing where justified, while leaving these different lifetimes explicit.

World response provenance is implemented with `HousingHomeUpdateSource::{Complete, Maintenance}` and a distinct crystal-rejection event. The decoded core regression verifies that invalid crystal profiles and valid or invalid maintenance deltas leave a full home query pending, and that dependent access loading starts only after a complete reply. Two decoded management regressions also prove that permission edits survive unrelated home/maintenance errors until HAR, and that abandonment survives access/maintenance errors but retires on an invalid complete home reply. This distinction is internal event semantics, not a fabricated wire request identifier.

Keep the consolidation bounded by named consumers: `housing_payment.rs` resolves candidates and invokes the world quote; `housing_execution.rs` interprets payment evidence; `housing_management.rs` interprets administrative evidence; `housing_queries.rs` coordinates reads. `busy_operation.rs` owns shared admission and terminal publication. The host projects these results, and the app-local crystal and management owners retain their distinct review and display lifetimes. Similar confirmation markup alone does not justify a shared transaction or review-state framework.

Subtraction targets are the vendor currency export, vendor-specific distance vocabulary, duplicated terminal busy publication, and any second housing quote or inventory fact traversal that integration would otherwise introduce. Do not add a generic payment draft, transaction framework, interaction controller, or drop registry as part of this work. The two housing UI surfaces share typed session facts and quote results, not a combined window/tab state owner.

## Flows and contract constraints

```text
Character initialized -> core HouseQuery
  -> HouseData / interpreted HouseStatus -> world home state
  -> core housing view -> host -> session snapshot -> Housing tab + home map marker

Existing Use(crystal) -> HouseProfile(crystal GUID, profile)
  -> world retains profile -> core publishes accepted interaction receipt
  -> host/session -> crystal HUD opens or replaces its current interaction

Drag into requirement cell / row auto-fill -> candidate draft
  -> core reads current inventory and world payment rules -> quote
  -> contextual action tab shows paid, selected contribution, outstanding, and excess per row
  -> payment click -> core revalidates and submits BuyHouse / RentHouse
  -> inventory and housing updates -> reconciled result -> draft refresh + existing toast path
```

- Home loading must distinguish unqueried/loading, no effective home, and loaded. Refresh retains the last known home while pending; timeout does not become no-home.
- Interpret HouseStatus by source meaning. ACE uses BadParam for an empty query result and HouseEvicted during login bookkeeping. Do not clear a valid home for every status indiscriminately.
- Preserve raw unknown wire values where needed, but do not synthesize actionable housing states from them.
- Compute current/account/other owner classification once in core. Roster membership proves account relationship; it does not prove the selected effective home or server configuration. AccountHouseId is not an established population path.
- The home wire data lacks owner/dwelling IDs. Do not invent a linkage from nearby positions. Management remains targeted by the server's effective-home semantics; show account owner labels only where proven.
- ACE's PropertyDataId HouseId/AccountHouseId and PropertyInstanceId HouseOwner lack SendOnLogin annotations. Their enum presence is not proof that the home owner can be known at login. An access-record roommate list also lacks an owner ID; absence from that list is not sufficient proof of direct ownership. Keep effective-home management eligibility explicit as known allowed, known refused, or server-determined. For server-determined owner-only actions, let ACE report eligibility through its existing feedback; never advertise a guaranteed capability or permanently suppress an action solely because its eligibility is unknown.
- Payment draft entries identify actual inventory objects, with unique IDs. The server chooses consumption amounts; do not promise user-selected per-stack quantities unsupported by the action.
- Quote against current inventory and payment progress. Distinguish consumed value from credited value; trade-note rounding can overpay. A quote is not a reservation and submission must revalidate.
- Auto-add preserves the existing draft, chooses only eligible carried inventory, fills remaining requirements, and reports insufficiency. Define deterministic selection that prefers exact coverage and avoids unnecessary note overpayment; it does not need a general optimal-payment solver. Preview actual ACE consumption for the chosen set.
- Buy requires full coverage; maintenance permits partial contribution. Prevent duplicate submission and overlap with conflicting inventory/trade operations using existing coordination.
- Keep machine-readable execution state separate from toast text. Preserve chat-only server messages without parsing English as transaction evidence. Avoid duplicate generic/housing notifications.
- HouseProfile has no client request ID. Bind local receipts to character/session, crystal, and active interaction; consume expected payment refreshes without reopening a dismissed window. Document any remaining same-crystal ambiguity rather than claiming perfect correlation.
- Closing a window must not erase an in-flight transaction's reconciliation owner. Teleport retires crystal interaction/draft; the effective home's retained information survives travel. Character/session exit clears character housing state.
- Full application replacement snapshots carry home/access/search facts and enough pending housing execution state to recover without losing a lock. A snapshot does not replay crystal-opening intent or recreate a dismissed draft. Resync invalidates candidate previews; views pull the replacement facts before accepting input again.
- Busy completion is operation-specific. `busy_operation.rs::finish_busy_operation_from_use_done` routes vendor continuation before taking the remaining active operation; add housing routing before that take. Generic errors can become pending evidence but must not imply housing failure merely because they arrived while payment was pending. Timeout, clear, and character-exit paths must publish a housing terminal outcome as they currently do for vendor execution.
- Marker placement derives from HouseData.Position through existing coordinates. Apartment state removes any previous marker and offers no Show on map action.
- Empty-hook visibility is not disclosed by the housing response. Use explicit Show empty hooks / Hide empty hooks commands with no selected/active state.
- Unknown individual permission booleans display unchecked as an accepted H3D presentation default. Preserve nullable disclosures in world/core; the display default is not authoritative knowledge. Reserve checkbox indeterminate state for genuinely mixed guest storage permissions.
